Yes — I get the plan, and I would adjust it slightly:

**Don't let the LLM directly change world state. Let it issue world intentions/commands. A deterministic orchestration layer translates those commands into subsystem-specific constraints, and the subsystem remains responsible for producing a valid state transition.**

That gives you:

```text
LLM
 │
 │ "Sharks FC defeats Turbo FC"
 ▼
World Director
 │
 │ interprets desired world change
 ▼
Action Plan
 │
 ├── football.play_match(
 │      Sharks,
 │      Turbo,
 │      constraint = Sharks wins
 │   )
 │
 ▼
Football Simulator
 │
 │ produces a VALID match satisfying constraint
 ▼
Match Result
 │
 ▼
World State
```

That distinction solves your nondeterminism problem.

### The LLM should describe desired facts, not manufacture implementation details

Suppose the model produces:

```json
{
  "intent": "sports.match.result",
  "home": "sharks-fc",
  "away": "turbo-fc",
  "desiredOutcome": {
    "winner": "sharks-fc"
  }
}
```

It is **not** saying:

```text
set score = 2-1
give player X goal
give player Y yellow card
move league points +3
```

Those are consequences that your football subsystem understands better than the LLM.

Instead your football handle receives:

```ts
football.playMatch({
  homeTeamId: 'sharks-fc',
  awayTeamId: 'turbo-fc',

  constraints: {
    winner: 'sharks-fc',
  },
});
```

The simulator could legitimately produce:

```text
Sharks 1–0 Turbo
Sharks 2–0 Turbo
Sharks 2–1 Turbo
Sharks 4–3 Turbo
```

The LLM doesn't care which.

It cares that:

```text
Sharks wins
```

became true.

## Your nondeterministic simulator is actually useful here

You don't necessarily want:

> LLM says Sharks wins → hard-code 2–0.

You want:

> LLM says Sharks wins → find one plausible simulation trajectory in which Sharks wins.

There are several ways to do that.

For your game, I'd start with **constrained resampling**.

```ts
function simulateWithConstraints(
  initialState: MatchState,
  constraints: MatchConstraints
): MatchResult {
  for (let attempt = 0; attempt < 20; attempt++) {
    const result = simulateMatch(initialState, randomSeed());

    if (satisfies(result, constraints)) {
      return result;
    }
  }

  throw new Error('Unable to satisfy requested world constraint');
}
```

So:

```text
Attempt 1
Turbo wins 2–0
reject

Attempt 2
1–1
reject

Attempt 3
Sharks wins 3–2
accept
```

The resulting game is still generated by your real simulator.

All the:

```text
passes
shots
goals
cards
fatigue
substitutions
player stats
```

are internally coherent because the football engine created them.

That is much better than having the LLM rewrite the score after the match.

---

Eventually you can make this smarter than brute-force resampling.

For example the simulation could accept **directorial bias**:

```ts
interface MatchDirectives {
  desiredWinner?: TeamId;

  strength?: number;
}
```

Then:

```ts
simulateMatch(state, {
  directives: {
    desiredWinner: sharksId,
    strength: 0.7,
  },
});
```

The simulator doesn't directly set:

```text
Sharks = winner
```

but can slightly influence things that are already probabilistic.

Perhaps Sharks gets:

```text
slightly better decision confidence
slightly better finishing variance
slightly more favorable tactical choices
```

until the requested story becomes likely.

But I'd be cautious with that because it can make your football model less interpretable.

**Resampling from different seeds is much cleaner initially.**

---

There should actually be different strengths of LLM instruction.

This is where I would adjust your idea the most.

The model needs to distinguish between:

### A. Hard world facts

> "Sharks FC defeats Turbo FC."

Must become true.

```ts
{
  mode: "constraint",
  winner: sharksId
}
```

### B. Soft narrative intentions

> "Sharks FC are expected to upset Turbo FC."

This should influence probability but doesn't have to happen.

```ts
{
  mode: "influence",
  preferredWinner: sharksId,
  strength: 0.4
}
```

### C. Open simulation

> "Sharks FC plays Turbo FC."

No desired outcome.

```ts
{
  mode: 'simulate';
}
```

That distinction is extremely important for your world.

Otherwise the LLM will accidentally become an omnipotent god every time it says something speculative.

## I'd call the middle layer the **World Director**

This is the component you're describing as:

> "something translates those plans into actionable items"

I'd formalize it.

```text
                  WORLD MODEL / LLM

                         │
                    WorldPlan
                         │
                         ▼
                  WORLD DIRECTOR
                         │
              validates + resolves
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
      Football        Economy       Geography
       Handle          Handle          Handle
          │              │              │
          ▼              ▼              ▼
      Football        Economy        World Map
       Engine          Engine          Engine
          │              │              │
          └──────────────┼──────────────┘
                         ▼
                    World Events
                         │
                         ▼
                    World State
```

The LLM never needs to understand how your football engine works internally.

It only needs to know that the world exposes something like:

```ts
worldCapabilities = {
  football: [
    'scheduleMatch',
    'playMatch',
    'transferPlayer',
    'hireManager',
    'fireManager',
  ],

  places: ['createSettlement', 'renamePlace', 'changePopulation'],

  economy: ['createCompany', 'changePrice', 'transferMoney'],
};
```

These are your **LLM handles**.

I like that name, actually.

## But handles should be semantic, not CRUD

Avoid exposing handles like:

```text
updateClub()
updatePlayer()
updateFixture()
setTableRow()
```

Those are too low-level.

Expose world actions:

```text
football.schedule_match
football.play_match
football.transfer_player
football.appoint_manager
football.injure_player
football.suspend_player
```

because these contain domain rules.

For example:

```ts
football.transferPlayer({
  playerId,
  fromClubId,
  toClubId,
  fee,
});
```

can automatically:

```text
remove player from old squad
add to new squad
transfer funds
create transfer history
update registrations
produce news event
```

The LLM only says:

> Musa transfers from Sharks FC to Turbo FC for ₦20m.

The subsystem handles everything that fact entails.

That's the same principle we established for your `MatchState`: **state should evolve through valid domain transitions**, rather than arbitrary mutations.

## This also means the LLM should read capabilities, not your database schema

I wouldn't feed it:

```text
Clubs table
Players table
Fixtures table
LeagueStandings table
...
```

and tell it to manipulate them.

Give it a contract like:

```ts
interface FootballHandle {
  playMatch(input: {
    fixtureId: string;

    constraints?: {
      winner?: string;
      loser?: string;
      draw?: boolean;

      minGoals?: number;
      maxGoals?: number;
    };
  }): Promise<FootballMatchResult>;

  makeTransfer(...): Promise<TransferResult>;

  changeManager(...): Promise<ManagerChangeResult>;
}
```

The actual database remains behind the domain.

That protects your world from garbage like:

```text
player is simultaneously registered to three clubs
team gets three points without a fixture
dead character becomes manager
city population becomes -5
```

The handles enforce rules.

## Then add a constraint hierarchy

This becomes important once your LLM starts telling stories.

Imagine it says:

> Sharks defeat Turbo 3–2 with Musa scoring the winner in the 89th minute.

That's much more restrictive.

Represent it:

```ts
{
  winner: "sharks",

  score: {
    sharks: 3,
    turbo: 2
  },

  events: [
    {
      type: "goal",
      scorer: "musa",
      minute: {
        min: 88,
        max: 90
      },
      requirement: "winning-goal"
    }
  ]
}
```

Your engine may or may not be able to generate that naturally.

So classify constraints:

```ts
type ConstraintStrength = 'required' | 'preferred';
```

Example:

```ts
{
  winner: {
    value: "sharks",
    strength: "required"
  },

  score: {
    value: [3, 2],
    strength: "preferred"
  },

  winningGoalScorer: {
    value: "musa",
    strength: "preferred"
  }
}
```

Then the director can say:

```text
Required:
Sharks win ✓

Preferred:
3–2 ✓

Preferred:
Musa scores winner ✗
```

and still accept the simulation.

This prevents you from endlessly resimulating because the model invented an absurdly specific scenario.

## The crucial rule: never silently overwrite the simulation afterwards

This would be the dangerous architecture:

```text
simulate match
↓
Turbo wins 2–1
↓
LLM wanted Sharks
↓
change database to Sharks 2–1
```

Now:

```text
Turbo players scored goals
Sharks somehow gets victory
player statistics disagree
match replay disagrees
league table may disagree
```

Your world loses causal integrity.

Instead:

```text
desired state
     ↓
generate valid path
     ↓
accept only path satisfying constraints
     ↓
commit entire path
```

That keeps everything coherent.

## This is essentially a transaction

You could treat each LLM-directed change as:

```text
PROPOSE
  ↓
PLAN
  ↓
VALIDATE
  ↓
SIMULATE
  ↓
VERIFY
  ↓
COMMIT
```

For your Sharks example:

```text
PROPOSE
"Sharks defeats Turbo"

PLAN
football.playMatch(fixture, winner=Sharks)

VALIDATE
fixture exists
both clubs eligible

SIMULATE
seed 51991 → Turbo wins ✗
seed 92381 → draw ✗
seed 12882 → Sharks wins ✓

VERIFY
winner == Sharks

COMMIT
save MatchState
save replay
save events
update league
publish world event
```

That would be the core of your **World Operating System**.

And this scales far beyond football.

The exact same mechanism can handle:

```text
LLM:
"Kola's population grows rapidly."

↓

world.demographics.changePopulation({
  place: Kola,
  direction: "increase",
  magnitude: "large"
})
```

or:

```text
LLM:
"A new railway connects Kola and Bira."

↓

transport.buildConnection({
  from: Kola,
  to: Bira,
  mode: "rail"
})
```

or:

```text
LLM:
"Sharks FC goes bankrupt."

↓

economy + football handles

close accounts
resolve debts
release players
remove club from competition
generate history event
```

The model specifies **what happens**.

Your systems determine **how the world can validly get there**.

That is the part of your original idea I would preserve most strongly: the LLM should be the **director/narrative planner**, not the physics engine, football engine, economy engine, or database administrator. Those subsystems are the "laws of your universe." The LLM gets handles that let it ask those laws to produce particular kinds of outcomes.
